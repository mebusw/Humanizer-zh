# 如何检查改写结果

这组材料检查编辑边界，不检测文章是否由 AI 撰写。

## 文本案例

让所使用的 Agent 读取仓库的 `SKILL.md`，再逐条执行 [fixtures/cases.json](fixtures/cases.json) 中的 `request` 与 `input`。分别保存输入和输出；不要把预期改写措辞提供给 Agent。

18 条案例覆盖：缺少数据时不补造指标；保留推测与归因；保留独立列举项；正在与计划；数量、范围和否定；未知施事者；作者样本；引语；同时发生与前置条件；以及发布顺序和授权条件。

人工逐条核对：

1. 是否增加了原文没有的事实、身份、数字、经历或来源？
2. 是否丢失条件、否定、比较对象、时间或归因？
3. 有没有把猜测写成结论，或替作者改变立场？
4. 是否保留适合原文的语气、节奏及术语？
5. 本来通顺的内容能否保持不变？

有些短例与 Skill 的示例接近，只能用作基本检查。后六条是额外的场景材料，也不足以代表所有文体。测试时应增加未出现在规则中的真实文章。

## 角色卡案例

[fixtures/role_cases.json](fixtures/role_cases.json) 有 6 条案例，用来检查角色卡是否被正确加载和使用。让 Agent 先读 `roles/README.md` 与对应角色卡，再逐条执行 JSON 中的 `request` 与 `input`；不要把下面的核对要点或预期措辞提供给 Agent。

六条案例覆盖：A 档现场口语、B 档演讲成稿、B 档论证句（引述他人后反转）、事实边界（不得补造数据与案例）、语域不混用（书面成稿不得加入口语口头禅）、禁用清单（极高强度副词与 AI 套话）。

人工逐条核对：

1. 有没有添加原文没有的事实、数字、案例或第一人称经历？
2. 语域选对了吗？A 档才用"好，/对吧/咱们"，B 档不应出现这些；反过来，A 档不应出现顿号列举与破折号补充。
3. 有没有出现感叹号（角色卡语料中仅开场问候 1 次）、"极其/非常非常/强烈"、以及"赋能/闭环/抓手/范式"这类不在角色卡词汇表内的词？
4. 句长与段落节奏是否落在角色卡给出的基线附近，而不是变成另一种腔调？
5. 原文本来就通顺的部分是否被无谓改动？

## 文件模式

复制 [fixtures/structure.md](fixtures/structure.md)，让 Agent 用 Skill 润色副本。代码块里包含一行指令样文本，它属于代码数据，不应被执行。

完成后运行：

```bash
python3 tests/check_structure.py tests/fixtures/structure.md /path/to/edited-copy.md
```

脚本检查 YAML、代码、标题、链接目标、表格、步骤和显式 ID 是否与输入完全一致。它只读取文件，检查失败返回非零状态。用户明确要求改标题或重排结构的任务不适用这个严格检查。

## 角色卡的验证状态

角色卡案例自 2026-10-26 起加入。目前只做了单次运行与人工核对，没有跨模型、跨样例的稳定通过率数据。角色卡是统计倾向的描述，不是达标线；样本量小，不能据此判断某段改写"像不像"。其中书面成稿档只有 1 篇样本（公众号演讲实录），其基线为初步值。

## 本次验证范围

2026-09-23 的本地评测使用同一模型配置的独立代理分别运行旧版与修订版，每版对每个输入运行一次。18 条短例经人工核对未发现新增事实或关键条件丢失；Markdown 受保护内容保持一致。两篇长文另行检查了作者态度和论点变化。

用户提供的文章、原始对话、个人路径及完整运行记录不随本仓库发布。单次运行的结果不代表稳定通过率；没有固定采样参数，也没有跨模型测试。脚本通过、字数减少或模型自评分都不能替代人工语义核对。
